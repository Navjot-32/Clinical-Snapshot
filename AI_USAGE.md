# AI Usage

I used AI throughout this assessment as a coding and review assistant. These notes
were recorded while I worked rather than reconstructed after completion. Generated
code and recommendations were treated as proposals requiring review, particularly
where an incorrect decision could change the clinical meaning of the source data.

## Tools and models

- **Claude Code**, through the VS Code extension, as the primary AI coding assistant
  throughout the build.
- **Claude Sonnet 5** for scaffolding, routine implementation, code generation, and
  test generation.
- **Claude Opus 5** for architecture and plan reviews, particularly for
  clinical-safety decisions where incorrect output could affect how patient
  information is presented.
- **Headless Chrome** for rendered-page screenshots and visual verification after
  implementation.

I retained responsibility for the architecture, normalization rules, clinical-safety
decisions, code review, and final verification.

## Where AI accelerated me

### Bundle analysis

AI helped catalogue the 17 FHIR resources and identify candidate issues such as
missing coding displays, unresolved references, invalid statuses, duplicate Patient
records, and inconsistent date precision. This accelerated the initial inventory, but
I reviewed every finding against the source bundle before using it in the
normalization policy.

### Project scaffolding

AI generated the initial FastAPI and Next.js structure, development configuration,
health check, and typed response skeleton. This reduced time spent on routine setup
and allowed me to focus earlier on reconciliation and clinical-safety rules.

### Test generation

After I defined the expected status and normalization behaviour, AI generated much of
the repetitive test matrix covering partial dates, resource-status buckets, patient
reconciliation, unresolved references, API behaviour, and resilience. I reviewed the
assertions and added adversarial cases that were absent from the generated suite.

### Version-specific documentation

Framework behaviour varies by Next.js version, so I directed Claude to consult the
documentation installed with the project instead of relying on model recall. This
exposed framework-specific behaviour that affected request caching and page
rendering.

## Where I corrected or rejected its output

### 1. I rejected an unsafe patient-matching heuristic

The bundle contains two Patient resources that appear to describe the same person.
Their names, gender, birth year, and address are compatible, and the assessment
explicitly states that the bundle is for a single patient. Their MRNs are not
identical, however, so the match is probable rather than authoritative.

Claude initially produced a generic scoring rule that merged records when enough
demographic fields agreed and none directly contradicted the match. It worked for the
supplied fixture and passed its generated tests, but the rule was unsafe outside that
fixture. Two members of one household could share a surname, gender, and address
while one record lacked a birth date. The heuristic could then merge them and attach
one person's medications or allergies to another.

I rejected the generic rule because household-level similarity is not sufficient proof
of identity. I replaced it with an assessment-scoped reconciliation policy:

- The reconciliation explicitly depends on the brief's single-patient bundle
  guarantee.
- `patient-001` is selected as the canonical record because it contains the more
  complete demographics and US Core profile.
- Compatible values are combined, while contradictory values are retained as
  conflicts rather than silently overwritten.
- The result is labelled as a probable duplicate resolution, not an authoritative
  identity match.
- Resources associated with `patient-002` retain their source provenance.

I added an adversarial regression test for two relatives at the same address. In
production, this responsibility would belong to an authoritative Master Patient Index
or a source-specific identity policy rather than this local reconciliation logic.

### 2. I rejected generated labels for unmapped clinical codes

Four codings contain a system and code but no human-readable display: ICD-10-CM
`E11.9`, LOINC `4548-4`, RxNorm `849574`, and SNOMED CT `91936005`.

Claude could provide likely descriptions from model knowledge, which would make the
page easier to read. I rejected that approach because model recall is not a verified
terminology source. A plausible but incorrect drug, diagnosis, or allergy label would
be presented to the clinician as fact.

The application therefore uses a deterministic fallback order:

1. `CodeableConcept.text`
2. Source-provided `Coding.display`
3. The original code and a normalized system name
4. An explicit "description unavailable" marker

No clinical meaning is generated by the model. The trade-off is reduced readability
and limited semantic deduplication, which is documented in the README. A production
implementation would resolve these codes through a versioned terminology service with
provenance and caching.

### 3. I corrected an unsafe approach to invalid and uncertain data

Claude's first plan filtered invalid resources and rendered whatever remained. That
created several problems.

- **Ambiguous empty sections.** If source allergy records existed but all were
  invalid or unusable, the UI could render an empty allergy section. A clinician
  might interpret that as "no known allergies," which is different from "all
  available allergy records were unusable." I introduced explicit section states so
  the response distinguishes populated, genuinely empty, uncertain, and unavailable
  data.
- **Invalid values leaking through quality notes.** The plan correctly excluded
  `observation-004`, which is marked `entered-in-error`, but proposed including
  excluded-resource details in the visible data-quality panel. That could
  reintroduce the invalid clinical value through a footnote. I separated clinical
  uncertainty from normalization audit information. Invalid resources contribute
  only resource identity and exclusion reason to audit metadata; their clinical
  values are not returned or logged. Regression tests assert that the excluded value
  does not appear in either the API response or application logs.
- **Status handling limited to the fixture.** The initial implementation handled
  only the status combinations exercised by the sample. The brief explicitly warns
  that the listed defects are not exhaustive. I replaced sample-specific
  conditionals with resource-specific status policies, including conservative
  handling for states such as `refuted`, `cancelled`, `on-hold`, `preliminary`,
  missing, and unrecognized. Unknown data is never promoted to a current clinical
  fact; allergies use a documented exception because hiding a possible allergy can
  be more dangerous than displaying it with an uncertainty label.

### 4. I verified framework and UI claims instead of accepting them

Claude initially added `cache: "no-store"` from habit. The installed Next.js
documentation showed that the relevant fetch behaviour had changed, making that
option unnecessary. More importantly, the production build showed that the page
could be prerendered and freeze the API state at build time. I changed the route to
render dynamically so a temporary backend failure during deployment could not become
the deployed patient summary.

I also did not accept the model's claim that the generated markup was visually sound.
I rendered the application in headless Chrome and inspected screenshots. This exposed
issues that type checking, production builds, and HTML assertions did not catch: long
clinical codes broke in the middle of tokens, a category label wrapped poorly, and
the data-quality indicator lacked sufficient visual prominence. I corrected the
layout and repeated the rendered-page check.

## Verification and limitations

AI generated a significant portion of the routine tests, but the expected behaviours
and safety boundaries were human decisions. The patient-matching false positive
demonstrated that tests generated by the same model as the implementation can share
its assumptions, so I supplemented them with adversarial cases and manually reviewed
the most safety-critical assertions.

The implementation deliberately does not attempt to be a general FHIR server,
terminology service, or Master Patient Index. Those boundaries are documented in the
README rather than hidden behind model-generated completeness claims.
